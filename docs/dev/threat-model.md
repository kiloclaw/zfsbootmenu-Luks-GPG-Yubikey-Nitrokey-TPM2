# Threat model

ZFSBootMenu runs before the operating system, holds the keys of encrypted volumes, and reads data that someone other
than its user may control. The rules about secrets in `crates/DESIGN.md` say how keys are handled; this page says
against whom, which inputs are hostile, what must hold, and what shows that it does. Every phase of
ROADMAP.md keeps it current: a change that adds an input, a secret or a privileged action adds a row here.

The page describes the Rust runtime and the host tools (`generate-zbm`, `zbm-kcl`). Where the legacy runtime differs,
it says so; the legacy runtime is frozen and is removed in R9.

## Zones and data flows

Today every process of the runtime runs as root in one zone: the supervisor (process 1), the start-up program, the
menu, the console on the display, the key methods and the recovery shell can all reach every secret and every device.
The arrows are the data that cross into it or out of it, with the attackers who control them and the assets they carry.

```text
             A1: ESP, image, EFI variables             A6: network (SSH, Tailscale, Tang)
                         |                                         |
                         v                                         v
  firmware --> ZFSBootMenu image (kernel, initramfs) -----+   SSH server (dropbear, the user's choice)
               I1 command line, I2 zfsbootmenu.conf       |        | key presses, a terminal (I10)
                                                          v        v
  +-------------------------- the runtime: one zone, all root --------------------------------------+
  |  supervisor (pid 1) -- start-up -- menu / console on the display -- recovery shell, hooks (I6)  |
  |                                                                                                 |
  |  in:  key presses (A2 keyboards: I10)      crypttab, key files (A2: I7)   pools, names (A3: I3) |
  |       LUKS headers, tokens (A1, A2: I8)    program output (I9)            EDID, fonts (I13)     |
  |  secrets S1-S3 --stdin pipes--> cryptsetup, tpm2_*, fido2-*, gpg, clevis --> kernel keys (S4)   |
  |  out: /dev/kmsg, journal, crash reports --> ESP when saved (S7, A1 reads them)                  |
  +---------------------------------------+---------------------------------------------------------+
                                          | kexec: kernel, initramfs, command line (S5)
                                          v
                              booted system (A4 as root, A5 without)
```

ROADMAP.md ("Processes and trust zones") splits this zone in four, Z0 to Z3: the supervisor, `zbm-unlock` (the only
process with secrets), the session, and the front ends, each with the least it needs. The keyholder of Z1 is there
(SB10): `zbm unlock serve`, a process that start-up or `zluks` starts for each unlocking run (I19). The console of Z3
is confined (SE11, P14), as user 0 still.

## Attackers

| Id | Attacker | Can |
| --- | --- | --- |
| A1 | Someone with physical access to the powered-off machine ("evil maid") | Change the ESP and the ZFSBootMenu image on it, the firmware's boot entries and EFI variables, and the unencrypted parts of every disk |
| A2 | A malicious USB device | Claim to be a key device (a file system with a key file or a crypttab), a keyboard, a FIDO2 or smart card, or a disk with a ZFS pool |
| A3 | Whoever controls the contents of a pool the user imports | Choose pool, dataset and snapshot names, `org.zfsbootmenu:*` properties, `keylocation`, `bootfs`, the files in a boot environment's `/boot`, and the hooks below a hook root |
| A4 | A process in the booted system | Read what ZFSBootMenu left behind: files, memory it did not wipe, mappings and keys it left loaded, logs |
| A5 | A remote user of the booted system without root | Everything A4 can, without root |
| A6 | Someone on the network, when the image runs an SSH server (`dracut-crypt-ssh`, dropbear) or joins a tailnet (`mkinitcpio-tailscale`) for remote unlocking | Reach the SSH server and try logins; read and change what crosses the network in the clear (DHCP, and clevis's requests to a Tang server), or answer as either; with a key the user authorised, use the menu and the recovery shell as root, as at the console |
| A7 | Whoever can change what goes into a build or an image: a crate on crates.io, a package of the build container's distribution, its base image, a GitHub Action | Put code into `zbm`, into the programs an image carries, or into the CI that builds releases |

## Assets

| Id | Asset |
| --- | --- |
| S1 | Passphrases and PINs the user types |
| S2 | Key files: in the image, on key devices, cached from `org.zfsbootmenu:keysource` |
| S3 | Secrets derived or unsealed at boot: TPM2 and FIDO2 secrets, YubiKey responses, GnuPG-decrypted keys |
| S4 | The keys of open LUKS mappings and loaded ZFS encryption keys, in the kernel |
| S5 | The integrity of what `kexec` starts: kernel, initramfs, command line, device tree |
| S6 | The machine staying usable: every failure ends in a message and a recovery shell, never in a hang |
| S7 | The logs and reports saved on the ESP (`zbm.save_logs`, `zbm report`): the kernel log, the journal, crash reports and a summary of the machine, which A1 and whoever mounts the ESP in the booted system can read |

## Untrusted input

Each input names the attackers who control it and the code that parses it. "Parser" means code that turns text or
bytes into values; each one in this table must fail with an error on hostile input, never panic or hang (P3).

| Id | Input | Controlled by | Parsed by |
| --- | --- | --- | --- |
| I1 | The kernel command line of ZFSBootMenu itself (`/proc/cmdline`, `zbm.*` options, `cmdline.d`) | A1 | `zbm_config` (`tokenize`, `ZbmArgs`, `ZbmOptions::parse`), `zbm_types` |
| I2 | `/etc/zfsbootmenu.conf` in the image | A1 | `zbm_config::conf::Conf::parse` |
| I3 | Pool, dataset and snapshot names | A3 | `zbm_types` (`PoolName`, `DatasetName`), `zbm_zfs::parse_table`; a filesystem's paths in ZFSBootMenu's state are made of its name with the pieces `mnt`, `kernels` and `kcl` escaped, so no filesystem's directory is another's or lies in another's mount point, kernel list or command line cache, though a child's directory lies inside its parent's (SB19; `zbm_state`, the property test `no_two_filesystems_share_or_nest_a_state_path`), and the library's `be_location` gives the same paths |
| I4 | `org.zfsbootmenu:commandline`, `:rootprefix`, `:kernel`, `:devicetree`, `:keysource`, `:active`, `:readonly`, `bootfs`, `keylocation` | A3 | `zbm_zfs`, `zbm_bootenv::commandline`, `zbm_bootenv::kernels`, `zbm_types::KernelSelector` (`:kernel`), `zbm_types::KernelArg` (`:rootprefix`) |
| I5 | Files in a boot environment's `/boot` and its `os-release`; its `/etc/resolv.conf`, its shell and the chroot's mount points, and the links on their way, in a chroot | A3 | `zbm_bootenv::kernels` (names, version order), `zbm_bootenv::commandline` (`os-release`); the chroot follows the links of `/etc/resolv.conf` inside its root, never in ZFSBootMenu's namespace (`zbm_tools::mount::inside`, whose property test `no_resolved_path_leaves_the_root` checks it), refuses a path into `/tmp`, `/proc`, `/sys` or `/dev`, and mounts the name servers on no link (SB15); its other mounts and its search for a shell follow no link of the environment either (SB16): the shell is looked for inside the root (`inside::resolve`), a mount point that is a link or passes through one is refused (`InRoot::first_link`; the property test `no_mount_or_unmount_target_passes_through_a_link`), and the teardown walks each path again and leaves one that a link now passes through to the root's recursive unmount; the root is mounted only on a path that passes through no link and no other mount, and its teardown checks by its mount ID that nothing of it stays mounted (SB16), unmounting by that path only while it still passes through none and the topmost mount on it is the root or one over it that is no other mount of the dataset, and reading the table again only while the root holds its ID, which the kernel gives to the next mount. The two races of the chroot root's mount ID, with another front end mounting the same dataset on the same path in the same instant, and with another mount taking an ID that the shell's own lazy unmount freed, are SB18's. The kernel's table of mounts is read by `zbm_tools::mount::table`, fuzzed by `mount_table`. The VM step is the chroot of `tplain/crafted` in `runtime-rust-recovery` |
| I6 | Hooks below `zbm.hookroot`, and `zbm.skip_hooks`, which names the hooks and built-in steps not to run | A1 (names the root, and the hooks to skip), A3 (fills the root) | `zbm_bootenv::hooks` (they are run, not parsed), and `zbm_platform::shell::interpreter`, which reads a hook's first bytes to tell how it runs; in Rust images, brush (`zbm-brush`) parses the hooks whose `#!` line names `sh` or `bash`, and those without one; `zbm.skip_hooks` is a list of names compared with the hooks' and steps' names (`zbm_startup`'s `skip_hooks`, `zbm_app::steps::skip`), never a path. A locked image takes no hook root, and on a locked or measured machine neither input removes the LUKS close (P15) |
| I7 | crypttab and key files on removable devices | A2 | `zbm_luks::config::load_config`, `zbm_luks::keyfile`; mapping names become `zbm_types::MappingName` before `cryptsetup` sees them |
| I8 | LUKS headers: `cryptsetup luksDump` text and JSON metadata, token JSON, the UUID of the default name `luks-<UUID>` | A1, A2 | `zbm_luks::tokens` (`parse_json_metadata`, `parse_dump_text`, `json_str`, `json_arr`, `json_bool`); `zbm_luks::device::default_name`, which parses the name as a `MappingName` |
| I9 | Output of the programs the runtime runs (`zpool`, `zfs`, `blkid`, `cryptsetup`, `tpm2_*`, `fido2-*`, `gpg`, `ykchalresp`) | A2, A3 through the data they print | the adapters of each program; `zbm_pool::hostid::scrape_hostid` |
| I10 | Key presses on the console, or in an SSH session | A2 (a fake keyboard), A6 (after a login) | the menu (`zbm-tui`), prompts; in the recovery shell, brush's line editor (reedline, or its basic editor on serial lines) |
| I11 | The state files of `/zfsbootmenu` (`luks-mappings`, `degraded`, command line caches, `steps`, the records of the built-in steps) | Only ZFSBootMenu itself writes them; listed because hooks (I6) can | `zbm_luks::mappings::parse_mappings`, `zbm_state` |
| I12 | EFI images that `zbm-kcl` edits and the stubs `generate-zbm` builds from, and `generate-zbm`'s configuration | The host's root user | `zbm_host::pe` (`Image::read`, fuzzed: `pe_images`), `zbm-kcl`, `generate-zbm` (host tools: trusted input, but they must not crash on a broken file) |
| I13 | The EDID of connected displays (`/sys/class/drm/*/edid`) and the headers of the image's console fonts | A2 (a display or adapter plugged in), A1 (the fonts) | `zbm_startup::autosize` (`edid::parse`, `font::cell`, `choice`), `zbm_display::psf` (`Font::parse`, `Font::subset`, at image build) |
| I14 | What programs write to the console on the display (`zbm.console=drm`), escape sequences included | A3 (names and files that programs print), A1 | `zbm_console::screen::Console` (`feed`, Alacritty's parser, and `draw`) |
| I15 | The directories and files on the ESP where logs and reports are saved (`EFI/zfsbootmenu/logs`, `reports`), and the record of each saved boot, `boot.json` | A1 | `zbm_boot::saved_logs` (`list`, and the pruning that keeps the newest boots): names are compared as text, never parsed into commands or paths outside that directory; `zbm_types::BootRecord::parse` (fuzzed: `messages`): at most 64 KiB, schema 1 alone, every text `Untrusted`, never made a path or a command; the menu's boot history (`zbm_boot::saved_logs::history`) reads them only with `zbm.save_logs`, from the ESP mounted read-only, `nosuid,nodev,noexec`, at a mount point of its own, at most 16 boots, 32 files of each and a record's 64 KiB, checked by size before it is read, and draws every name and text through `Printable` |
| I16 | What crosses the network for clevis's Tang pin, and DHCP | A6 | `clevis` and `curl` (programs; their output is I9), the initramfs's network modules; the image's `/etc/resolv.conf`, which DHCP fills, is bound read-only into a chroot (SB15): no crate parses it, and the names a chroot resolves are only as trustworthy as the DHCP server's name servers |
| I17 | Messages on the session's socket, `/run/zfsbootmenu/session.sock`, and the console's control socket, `/run/zfsbootmenu/console.sock` (`SOCK_SEQPACKET`, at most 64 KiB a message) | Root only: the directory is root's, and each socket refuses a peer the kernel names as another user (`SO_PEERCRED`); A6 once logged in as root | `zbm_app::session` (`Request::decode`, `Answer::decode`), a remote menu's messages after a takeover (`zbm_app::remote`: `ToSession` and `ToMenu`, at most 16 MiB in parts, a secret's length checked against its packet, every name parsed again; the terminal's descriptors, at most four, closed on `exec`; the actions that take the console run in the session on that terminal, each program in a session of its own without a controlling terminal, so that `/dev/tty` never reaches the session's console; an answer to what the session's action asks, `ToSession::Answer`, goes only to the question asked now, by its number, and the session opens only a volume it lists, one at a time) and `zbm_app::console` (`Request::decode`, `Reply::decode`; a layout's name is a word of the image's list, never a path), JSON through `serde_json` |
| I18 | Messages on the client channel between the console on the display and the menu (ADR 0004, UI6): a socket pair the supervisor makes, its ends passed to the console (`--cells-fd`) and to the start-up program (`ZBM_CELLS_FD`), never to the recovery shell (`SOCK_SEQPACKET`, at most 64 KiB a message): cells and the cursor from the menu, keys and sizes from the console | ZFSBootMenu's own processes; a program the start-up program starts inherits nothing (the descriptor is closed on `exec`) | `zbm_display::channel::wire` (`FromClient::decode`, `FromConsole::decode`: exactly one message, at most 4096 cells of 64 bytes each, a cell's text cut at a character); the console keeps the cells inside its grid and shows control characters as spaces (`zbm_console::screen::cells`) |
| I19 | Messages between a client (start-up, `zluks`, the menu on the console and the session for the menu over SSH) and the keyholder it started, `zbm unlock serve` (SB10): a socket pair, the keyholder's end passed in `ZBM_KEYHOLDER_FD` (`SOCK_SEQPACKET`, at most 64 KiB a message): the action, whether the person who answers is over SSH, and the answers to its requests from the client, a secret as a packet of its own; the requests, notices and events from the keyholder | ZFSBootMenu's own processes: the keyholder takes the end its parent passed, of its own user (`SO_PEERCRED`), and a program either starts inherits nothing | `zbm_app::keyholder` (`ToKeyholder::decode`, `FromKeyholder::decode`, JSON through `serde_json`; a secret's length at most 64 KiB, and a packet of another length is wiped and refused) |
| I20 | What a Braille display sends over USB or a serial line, in images built with `zfsbootmenu_brltty=yes` (ADR 0011) | A2 (a device plugged in that claims to be a display) | `brltty`, a program of root that the image starts before anything is asked; its drivers are the ones `/etc/brltty.conf` names. Images without the option hold no `brltty` |
| I21 | Requests on the socket pair between the console on the display and the supervisor, which opens its devices for it (ADR 0012): a kind and a path | The console (zone Z3), once a parser of what programs print (I14) is compromised | `zbm_app::devices` (`Request::decode`, JSON through `serde_json`; `open_checked`: the name must be one of the kind's below `/dev`, the node a character device of the kind's numbers before and after it is opened, never a link); fuzz target `messages` |

## What must hold

Each property names the attackers and assets it is about and what shows that it holds. "Holds" means a test, fuzz
target or review shows it; "to verify" means it is believed to hold and the evidence is still owed, by the phase named.

| Id | Property | Against | Evidence | Status |
| --- | --- | --- | --- | --- |
| P1 | No secret reaches a command line, an environment variable, a file or a log: secrets go to programs on standard input and come back as `Secret`, which is wiped when dropped and prints as `Secret(..)` | A4, A5 on S1 to S3 | `crates/DESIGN.md` (Secrets); the `Secret` type; `FakeSystem::assert_no_leak`, which the key method tests end with; the journal (`/zfsbootmenu/journal.jsonl`) writes only the fields of an allow-list (`zbm_trace::KEPT_FIELDS`), any other as `[redacted]`; `Secret` is not `Clone` (copies are `duplicate()`, commands and actions share one behind an `Arc`) and compares in constant time (`ct_eq`); key files cached from key sources are written new with mode 0600 (`O_CREAT \| O_EXCL`) and removed before `kexec` | Holds for the Rust runtime. The legacy runtime writes GnuPG-decrypted keys and unsealed TPM2 and FIDO2 secrets to files below `/run` and passes a salted TPM2 PIN to `openssl kdf` as an argument (`legacy/RUNTIME-CHANGES.md`) |
| P2 | No secret outlives its use in ZFSBootMenu's memory: an unlocking run is a process of its own, the keyholder, and drops its secrets when it ends; nothing secret is left in `/zfsbootmenu` | A4 on S1 to S3 | The process design (`crates/DESIGN.md`); the VM tests check that a keyholder opened the volume; the Rust key methods capture into `Secret` ; `Secret` keeps them in locked pages, out of core dumps and child processes, and out of the kernel's map of memory where `memfd_secret` is enabled; the runtime's processes are undumpable; the VM tests `secrets-passphrase` and `secrets-keyfile` search every process's memory, command line and environment, and every file in memory, just before `kexec` | Holds for secrets the runtime creates: the VM tests found neither secret anywhere (October 2026). A hook of that name in the image itself still replaces the step: the image is the owner's, and A1 who changes it is R3's. A locked image without lockdown or Secure Boot is warned about at start-up: a changed kernel command line gets past the lock. Elsewhere `zbm.skip_hooks` and a hook root still remove the close, as in the legacy runtime, which keeps it a script on every machine |
| P16 | What the runtime hands hooks holds no secret: their variables, and the context file `ZBM_HOOK_CONTEXT` names, `/run/zbm/hooks/<stage>.json`, which the runtime writes before a stage that runs a hook file (mode 0444, root's, in RAM) and removes after it. The file says what the stage knows (pools, the boot environment, the selected kernel, the command line, the lock, lockdown and Secure Boot), never a key location's contents | A4, A5 on S1 to S3; A3 (a hook root's hooks read it) | `zbm_bootenv::hooks::context` and its tests: the fields of each stage, unknown values `null`, no file for a stage of built-in steps alone, the file removed after its stage; the stage variables come from one function (`HookEnv::vars`), tested for every stage; P1's `FakeSystem::assert_no_leak` | Holds for the Rust runtime. The file is not measured: the runtime writes it, and the hooks that read it are the image's or measured (ADR 0009). Hooks run as root (R1), so a hook can still change it for the hooks of its stage after it |
| P17 | Every interactive shell opens through the one gate (ADR 0010, SE9): in a locked image, only after the PIN. The chroot does too, from the menu, from the recovery shell (`zfs-chroot`, `zbm`'s applet, which asks for the PIN as `zbm lock shell` does) and from a hook (ADR 0018, point 8). The library that hooks source goes through it: its `emergency_shell` runs `zbm zfunc emergency_shell`, the start-up program's gated recovery shell, and its `zfs_chroot` runs `zbm zfunc zfs_chroot`, which runs `zfs-chroot`; so do the `emergency_shell` and `zfs_chroot` of a legacy function that `zbm zfunc` runs on Bash | A1, A2 (a keyboard), A6 on S4, S5 | `zbm_app::auth::ShellGate`, the only way to a shell, and the unit tests that every shell start goes through it; `xtask metrics`' `shell_starts`, which counts the gate's start alone; `zbm_app::auth`'s `without_authority_nothing_is_imported_or_mounted`; `zfs-chroot`'s `a_locked_image_asks_for_the_pin_before_the_chroot`; `zbm_startup::zfunc`'s `the_emergency_shell_goes_through_the_gate`, and its `the_hook_s_chroot_leaves_the_pin_to_the_applet`, which shows that `zfs_chroot` opens nothing itself and runs `zfs-chroot`, locked or not; `zbm_tools::programs`' legacy function, which defines `emergency_shell` and `zfs_chroot` as `zbm`'s; the VM test `integrity-locked`, whose recovery shell's `zfs-chroot` asks for the PIN again | Holds for the Rust runtime. `zbm zfunc` asks for the PIN for `emergency_shell` and `zfs_chroot` alone, both through their applets: hooks are the image's or measured, and the recovery shell is behind the gate already. A chroot from the recovery shell or a hook asks for the PIN again, since each process keeps its own proof. The legacy runtime has no lock |

## Risks that stay

These follow from features users rely on. They are documented so that users can choose, and so that a change does not
make them worse without saying so.

| Id | Risk | Why it stays | What a user can do |
| --- | --- | --- | --- |
| R1 | Hooks below `zbm.hookroot` run as root. Whoever controls the kernel command line (A1) or the device it names (A2, A3: a disk with the same label or UUID) runs code in ZFSBootMenu, also on a machine whose volumes unlock themselves with the TPM, where nobody is there to notice | Hooks are the extension point of ZFSBootMenu; the hook root is mounted in `40-early-hooks`, before any volume opens or pool imports, so no unlock or import policy can judge it | Sign the image with Secure Boot (A1); keep `zbm.hookroot` off a machine that unlocks itself, or put the hooks in the image; [ADR 0009](adr/0009-hook-root.md) measures the hook root into PCR 9 before its hooks run, so a TPM2 token bound to PCR 9 (enrolled with `zbm measure unseal`'s value) unseals only with the hooks it was enrolled with; the hooks still run, and a token bound to other PCRs is as before. A file of the hook root that `cp` fails to copy is disabled where it was left, so what is not measured does not run. Lock the menu (`zfsbootmenu_lock_hash`, SE9): a locked image ignores `zbm.hookroot`. Under lockdown or Secure Boot a hook root cannot replace the LUKS close (P15) |
| R2 | A disk plugged into the machine (A2, A3) is imported, and its `bootfs` can become the default boot environment when no pool is preferred | Importing every pool is the default, so a moved disk boots | `zbm.prefer=pool!!` imports that pool and no other; `zbm.prefer=pool!` requires it but imports others after it. An import policy that refuses foreign host IDs (`zbm.import_policy=strict`) keeps pools of other machines out. After an unattended unlock this is the default: `hostid` imports as `strict`, and a boot environment on no unlocked volume boots only when chosen (ROADMAP.md SE10) |
| R3 | An image on the ESP is not authenticated by ZFSBootMenu (A1) | The firmware decides what it starts | Secure Boot with your own keys; `generate-zbm` signs images through its post hooks (`PostHooksDir`) |
| R4 | After `kexec`, the memory of ZFSBootMenu's kernel is not wiped; the new kernel hands only zeroed pages to its processes, but root in the booted system can read physical memory where the kernel allows it | `kexec` replaces the kernel without a reset | Boot environments with `CONFIG_STRICT_DEVMEM` and lockdown; `init_on_free=1` on ZFSBootMenu's command line, so that its kernel zeroes the pages it frees (`zbm report` says whether it does); P2 keeps secrets the runtime created out of that memory as far as it can, and the runtime drops the page cache before `kexec`. Buffers the kernel still holds at `kexec` (terminal and input buffers it reuses) are not wiped |
| R5 | `Ctrl-R` in the unlock dialog shows the passphrase being typed (proposed in `docs/dev/menu-design/unlocking.md`), so whoever sees the screen, or a camera, reads it (S1) | A passphrase set with another keyboard layout cannot be typed blind; seeing it is how the user finds the layout that works | It is off at every prompt and never on by default; the text is drawn only while the dialog is open. Turn it on only at a console nobody watches |
| R6 | Sealing a TPM2 key again (the re-seal alert, ROADMAP.md #11) trusts the machine as it is when the user confirms. If A1 changed the firmware settings or the boot path, the TPM then releases the key to that state (S3) | After a firmware update the user would otherwise type the passphrase at every boot | The alert lists each PCR that changed and what the event log says about it, and is for changes the user made; it needs the volume's name typed. Decline it when a change is unexplained, and keep using the passphrase |
| R7 | The shell of Rust images is brush, younger than Bash and less used. A script that behaves differently on it, or a bug in its parser, can make a hook do something other than what its author meant (S6) | brush is the shell of the Rust runtime (`ROADMAP.md`, decisions); the hooks are code the user already trusts (R1) | `zbm.shell=bash` runs everything on Bash; a hook can name another interpreter on its `#!` line; the recovery shell falls back to Bash when brush does not open |
| R8 | Whoever logs in over SSH (A6, with a key the user authorised) is root in ZFSBootMenu: the menu, the recovery shell and every pool, as at the console | Remote recovery is what the SSH server is for | Restrict the key in `authorized_keys` (`command=`, `from=`); keep the SSH server out of images that do not need it; lock the menu (`zfsbootmenu_lock_hash`, SE9): the shell and every change then need the PIN over SSH too, the shell a hook or a library function opens included (P17). A volume opened over SSH with its passphrase or PIN, in the menu, by start-up run from it, or with `zluks`, is recorded as opened remotely: unlike one opened at the console, it opens nothing the locked menu keeps. A login with a shell can write that record itself, which is why the key should be restricted to the menu |
| R9 | `brltty` (`zfsbootmenu_brltty=yes`) runs as root, unconfined, and parses what a USB or serial device sends (I20) before the menu: a flaw in it, reached by a device that claims to be a Braille display (A2), runs code in ZFSBootMenu | A person who reads with a Braille display needs it before anything is asked | Leave the option off images whose users need no Braille display; name the one driver and device of the display in `/etc/brltty.conf` rather than `auto`, so that `brltty` speaks to that device alone |
| R10 | Entering a chroot of a boot environment runs that environment's programs (the shell's probe, then the shell) as root, with every capability, in ZFSBootMenu's mount namespace and with its `/proc`, in every mode, read-only and snapshot chroots included: a crafted environment (A3) has ZFSBootMenu from then on, and can change the image's mounts and the firmware's variables | A chroot is for repairing an environment, which needs its programs | Enter a chroot only of an environment you trust as you trust ZFSBootMenu; SB16 keeps ZFSBootMenu's own mounts and unmounts inside the root; confinement in namespaces of its own is SB18 |

## Out of scope

- Compromised firmware, or an attacker who can run code as root before ZFSBootMenu starts.
- Attacks on the cryptography of LUKS, ZFS native encryption, TPM2, FIDO2 or GnuPG themselves, and on the hardware
  tokens.
- Side channels (timing, power, electromagnetic) and cold-boot attacks on RAM.
- Denial of service by an attacker with physical access, who can always switch the machine off.
- The booted operating system's own security once `kexec` has started it, except what ZFSBootMenu leaves behind (A4).

Findings so far:

- `program_output`, on its first run: `zbm_pool::hostid::scrape_hostid` sliced the output of `zpool import` at byte
  positions, and panicked when text that is not ASCII came before `hostid=`. A pool someone else controls (A3) could
  stop the start-up program with it. Fixed, with the input as a unit test.
- `console_replies`, by review while it was written (SE5): the console on the display answers a program that asks
  for its colours (`OSC 10`, `11` and `4`), and the menu's key decoder read the answer as Alt+`]` and the letters of
  the colour. A file of a pool shown on the console (A3) could type into the menu. The decoder now drops the string
  sequences terminals reply with, and a C1 control typed as a character; unit tests in `term_keys` and `zbm`.
- `key_input`, on its first runs (SE5): the menu's terminal key decoder lost or doubled Enter at the edges of broken
  input. A stray byte that starts a UTF-8 character, `ESC O` or a control sequence cut short took the Enter after it
  as part of themselves; and the reader, which joins CR LF cut between two reads, kept dropping line feeds after the
  first. Over SSH or a serial line, that could skip or confirm a dialog. Fixed: a broken character or sequence ends
  at the first byte that cannot belong to it, and only the byte right after the carriage return of an Enter is
  joined to it; the inputs are unit tests in `term_keys`.
- `menu_names`, once it said every view and dialog in the line view's words too (UI10e): the line view and
  `Announce` printed what the machine says as it came, in start-up's stages, the progress and notification lines,
  the questions, the unlock dialog's notice, the dialogs' lines and the command line being edited; and the packages
  segment drew a package database's manager and versions so, whose bidi controls reached the cells. A volume, a
  device or a boot environment's package database (A2, A3) could reorder or act on the line view's terminal. Fixed:
  the words leave `view::words` printable, and the packages segment draws them through `Printable`; unit tests in
  `lines` and `view`. On its first run it also found that the classic map's rollback confirmation added the sizes
  of the newer snapshots without a bound: sizes a pool gives (A3) that add up past 2^64 overflowed, which ends the
  menu, as overflow checks are on. The sum now stops at the largest; a unit test in `update`.
